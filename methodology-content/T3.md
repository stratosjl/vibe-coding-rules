# Methodology slice: T3, serious project (cumulative T0 + T1 + T2 + T3)

First line of EVERY reply from the time this slice is loaded (whether at SessionStart or mid-session via `/tier`, `/raise-tier`, or `/lower-tier`) until session end MUST be exactly the following literal text (NO surrounding backticks, NO surrounding quotes, NO code block). v1.13.0 clarifies: the rule applies to every reply, not only the first reply after slice load.

Detected tier: T3 (S<x>/C<y>), <label>. Override with /vc-roe:tier <T0..T4> if wrong.

## What T3 is

Multi-stakeholder OR multi-machine OR multi-month with irreversible actions in scope; OR any project at criticality C2 (regulatory exposure, MNPI, public communication, financial transactions, regulator-compellable artefacts). Full operator standing-rule discipline applies. Full canonical: the canonical methodology specification v4.1 §2 T3.

### Added at T3

1. **Audit-pass policy** (`feedback_audit_pass.md`). Owed when session touched architecture, theme defaults, deploy pipeline, security boundaries, or any irreversible production change. Most content/discovery/housekeeping sessions do NOT owe audit-pass. Every handover ends with one-line `Audit-pass owed for THIS session: Yes / No` footer + reason. INTER-session, no scope gate; operator confirms before optimisation begins.
2. **Lessons-promotion path.** Pattern surfacing 3+ times across handovers gets promoted: one-line standing rule in project CLAUDE.md, or `~/.claude/projects/.../memory/feedback_*.md` for cross-project patterns.
3. **Explicit irreversible-action enumeration** in project CLAUDE.md. The list is what the confirmation-gate matches against. [EXAMPLE-PROJ] §6 reference instance: deploys, force-pushes, schema migrations, external sends, branch deletes, dependency removals.
4. **Four-pass closing matrix + CA3 hybrid handover split** (`feedback_traceability_matrix.md`; matrix extended 2026-05-01 from two-pass per D-MET-34; CA3 hybrid landed v0.2.1 per D-MET-51). Pass 1 = positive-scope edits (`ID | Edit | Location`). Pass 2 = forward obligations (`ID | Obligation | Owner | When`). Pass 3 = scope discipline, two sub-tables: coverage check (`ID | In-scope item | Status`) + drift entries (`ID | Drift entry | Reason`). Pass 4 = end-of-session sweep, two sub-tables: idea-bank capture check + open-issues capture check. Mandatory at every handover. Supersedes T2 lighter sweep paragraph. **Handover splits into TWO files at T3+:** `handovers/session-NN-summary-YYYY-MM-DD.md` (1 to 3 KB target / 5 KB ceiling; tier + verdict + what shipped + what is pending + opening prompt at bottom + pointer to audit-trail) plus `handovers/session-NN-audit-trail-YYYY-MM-DD.md` (5 to 15 KB target / 30 KB ceiling at T3; full four-pass matrix + audit-pass discharge inline + lessons + verification block). Next-chat opening prompt rendered as fenced block in final chat message; chat-render is a separate obligation from writing it into the summary and never substitutes.
5. **Anomaly-first reflex** (`feedback_anomaly_first_reflex.md`). Unexpected signal → pause, root-cause, capture as OBS row before continuing (formal escalation of T2 item 10 inline callout). Never paper over an anomaly to ship. Smoke-test before any >2-min probabilistic batch; auto-abort on degenerate output; first contradictory signal triggers pause-and-probe (not log-and-continue).
6. **Regulator-presentable exactness** (`feedback_regulator_exactness.md`) when work has C1 or C2 component. Canonicalise compliance counts and labels on enumeration; propagate to all dependent artefacts; never leave a partial canonicalisation drifting.
7. **Best-practices-first** (`feedback_best_practices_first.md`). Judge every implementation/scope/sequencing decision against four axes: performance, project management, security, scheduling. Engineering rigour over minimal-effort heuristics; do not default to path-of-least-resistance.
8. **Long-process status checks** (`feedback_long_process_status.md`). Any operation >10 min gets a stuck-check + on-screen status update every 10 min until done.
9. **Capture every idea** (`feedback_capture_ideas.md`). Default to adding entries to the project idea bank mid-conversation, not at session end. Surface OPEN entries proactively when relevant.
10. **Three-same-day-override pattern** (`feedback_pattern_3x_override.md`; codified at session 10 of Tiered Methodology Consolidation; promoted to canonical at v0.2.0). When three same-day operator overrides of a soak-window deferral happen on coupled architectural surfaces, halt the same-day-patch cadence; the fourth touch MUST be a comprehensive batch closing all known follow-on issues, not another isolated patch. The pattern itself is the signal that the original ship was under-batched. Bundle all accumulated defects into the fourth ship; soak window resets ONCE for the comprehensive batch.
11. **Deferral closure-date discipline** (`feedback_deferral_closure_dates.md`; promoted at v1.7.0 from `OBS-vcroe-audit-patterns-self-leak-01` closure lesson at v1.6.0). Architectural deferrals labelled "known risk" (leak risk, correctness risk, regulatory risk) MUST carry a date-gate, version-gate, or coupling-gate closure trigger, never an open-ended "defer to future session" annotation. Concrete trigger forms: ISO-8601 closure date, semver gate (e.g., "close before next minor"), or coupling gate (e.g., "close before next history-rewrite ship"). Deferrals without a trigger become latent regulatory exposure; the v1.1.4-to-v1.6.0 W2 deferral (~3 weeks, 6 ship cycles, ultimately requiring force-with-lease and history rewrite to close) is the reference incident. At session open, any forward-obligation or OBS row without a closure trigger is surfaced and the trigger set before continuing.
12. **Source-of-truth chain** (added v1.15.0). The project's forge remote is the canonical source of truth; the local working folder is the working surface. (1) On project resumption, reconcile the working folder against the canonical forge BEFORE substantive work begins; any divergence (uncommitted changes, ahead/behind the upstream) is an operator decision point: surface it and agree a sync direction, never silently resolve it. (2) **At session close the session itself commits and pushes** session-meaningful local changes to the forge, then confirms the push landed by asking the remote. Handing the push to the operator as a closing instruction does NOT discharge this (added v1.25.0): it converts a close obligation into a manual step performed later or not at all, and the canonical copy is stale until it is. The push is authorised by this item, so do not re-ask for it at close; what still needs the T1 confirmation gate is the irreversible-action list, a force-push above all. **Verify against the remote, not against the tracking ref.** A local `HEAD...@{u}` comparison reports level when the tracking ref is stale, and reports `0 0` when the branch's configured upstream does not resolve at all, so the check that appears to pass is the one that never looked; ask the remote for the ref and read back the sha that landed. A session with no session-meaningful change discharges this by saying so in negative scope. **This authorises the push, not the staging**: commit the paths the session named and no others, because a working tree can carry another session's uncommitted work. (3) Projects are private-by-default unless the operator has explicitly classified them public. An operator whose infrastructure needs richer resumption state (self-hosted forges, jurisdiction-restricted residency routing, disaster-recovery copies) supplies that through the machine-local SessionStart addon seam (v1.15.0), keeping this public requirement provider-agnostic.

13. **Handover re-audit and prompt-carrying, at T3 exactness (added v1.21.0).** T2 items 15 and 16 are inherited and sharpened by the CA3 hybrid split. When the handover is split into a summary and an audit trail, the re-audit covers **both files**, because a late result can invalidate the summary's headline while leaving the trail's evidence intact, or vice versa. State in the trail which artefacts were re-audited and against what.

    The T3 addition is that **the re-audit is itself evidence**. Record that it ran, what it changed, and what it deliberately did not change. A close that says "handover written" and a close that says "handover written, then re-audited against two results that arrived afterwards, one instruction corrected" are different claims, and only the second is defensible when someone asks months later why the next session did what it did.

14. **A multi-agent run is DURABLE BY CONSTRUCTION, or it is not evidence (added v1.25.0).** T2 item 12 governs when to reach for a subagent. Nothing governed what happens when a run of them is interrupted, and on any fan-out worth orchestrating that is the normal case rather than the exception. The clauses below come from this plugin's own whole-repository review of 2026-09-04, across four orchestrated runs that between them lost work in five different ways. Each carries its evidence, and where a clause is design reasoning rather than a measurement it says so on its face.

    **(a) An agent's result is not durable until the agent writes it somewhere.** A return value lives in the orchestrator's memory until the run completes. Instruct every agent to write its complete structured result to a named path as its LAST action, read it back, confirm it parses, and report the path. Measured: a triage run was stopped with about ten agents in flight and none of their results arrived, so ten files stood edited by the agents that had judged the findings and nothing had checked any of it. That work reached no consumer for one reason, that it existed only as a pending return value. It was not gone: the ten transcripts still held it, which is exactly why clause (b) exists and why the honest word is unreachable rather than lost. Compliance is achievable once it is instructed: 62 of 62 agents in one run and 52 of 52 in the next persisted correctly.

    **The rule paid for itself the same day.** A later run lost its network mid-flight and the orchestrator reported an agent as FAILED, unreachable API, no result. That agent had already finished and written three complete adjudications to its path. Its return value was destroyed and its work was not. Persisting converts a loss that looks total into one that costs a single message.

    **(b) An agent also leaves structured, recoverable output IN ITS OWN TRANSCRIPT, so an interrupted run can be RESUMED rather than restarted.** The write in (a) happens once, at the end, and a hard kill lands before it; a transcript is appended while the agent works and survives whatever kills it. Instruct each agent to emit a machine-readable checkpoint into its own output after each item it finishes, not only at the end: a fenced block behind a stable marker, carrying the item, what was done, and the outcome. The next session then recovers the completed items and re-dispatches only the remainder. Without it the honest options are to discard the run or to repeat it whole, and repeating is what happens, because discarding feels wasteful and nobody can tell how much was already done.

    **(c) Commit the accumulated table to the repository before the next phase.** Not because the run directory is deleted: a later session read a previous session's 94 transcripts and its scratchpad without difficulty, so "swept at session end" is a claim this fleet has measured and found false, and clause (b) depends on it being false. The reason is discoverability. A run directory is addressed by a run id that appears in one notification and in no artefact anyone reads, so a verdict table that took a hundred agents to produce survives on disk and is unreachable by anyone who does not already know where to look, while the branch it describes is in front of everybody.

    **(d) Prefer a pipeline to a barrier.** A barrier waits for every task in a stage before any of the next begins, so one wedged task holds the run and every completed result behind it is unusable while it waits. Pipeline each item through its own stages instead, so one item can be in stage three while another is still in stage one, and reserve a barrier for a stage that genuinely needs every prior result at once. **This clause is design reasoning and not a measurement, and the difference is recorded on purpose:** the fan-out that prompted it, 85 verifiers behind one barrier, was written up as a structural stall and was nothing of the kind. See clause (j) for what it actually was, and for why the write-up was wrong.

    **(e) Never signal "nothing to do here" with a NULL RETURN from a stage, and RECONCILE THE AGENT COUNT against what you dispatched.** In a harness where null marks an agent that died, a stage returning null drops the item and skips every later stage for it. Measured: a four-stage pipeline over 24 files, whose first stage returned null for the 22 that needed no re-judging, spawned 4 agents in total, and those 22 files never reached the stage that does the work. The 4 is the orchestrator's own agent count for the run; the expected number is items times the stages each item is due, which is knowable before the run and was not 4. Nothing errored on their behalf and the run summary named no dropped item. Return a sentinel object. Then check the arithmetic anyway: items times stages is a number known before the run starts, and a disagreement with the orchestrator's own agent count is work that silently did not happen, reported by no other surface.

    **(f) One orchestrated run at a time.** Concurrent runs contend for the same session capacity and the failure is not graceful: the second run's agents die on a limit rather than queueing.

    **(g) Assignment integrity is asserted BY THE AGENT, in its own briefing, before it does any work.** Give each agent the means to check that the work it holds is the work it owns, and instruct it to stop and report rather than proceed. Measured: in a run dispatching one agent per file, 74 of 88 verdicts were rendered by an agent that owned a different file from the one the finding was about, and 27 of 27 agents were affected. And what they did about it is the finding. Measured over the same 27 result payloads, with the criterion stated as "the agent's report to the operator names a routing or assignment fault" and both controls passing: **11 of 27 named it, 10 of those declined to edit anything, and NOT ONE of the 27 declined to judge.** All 88 verdicts were rendered anyway. So the failure is not that nobody saw it; it is that seeing it did not stop anybody. That also explains the run's headline of 78 of 79 confirmed: an agent judging a claim about a file it is not reading confirms the claim as written.

    **And the run written to CORRECT that mis-dispatch reproduced it**, which is why the remedy is mechanical rather than a resolution to be careful. The orchestrator generated a correct grouping to a file, then hand-transcribed all 84 ids into the dispatch instead of passing the generated file through. Three of 27 packages carried an error: one swapped pair between adjacent packages, and one mangled name that later made a completed package read as missing. Two seats refused outright and named the swap. One of them also showed that the package summary could not have caught it, because its correct set and the set it was handed were each four findings with two rated high; the other seat's sets were three findings with none rated high, so that particular argument is one seat's and not both. **The grouping an agent receives must be the grouping a program produced, passed through unedited, and the agent must be equipped to prove it.**

    **(h) The seat that judges is not the seat that fixes.** An agent asked to adjudicate a finding and repair it in one breath will confirm it. Judge first; adversarially refute the survivors from a second seat told to default to refuted; only then dispatch a fixer; and give the fix to a fourth seat that made no edit and is told to break it. Measured worth: the refuters killed 13 of 69 confirmations, and the verifying seats caught two defective fixes plus three defects that an earlier unverified edit had introduced into a live hook.

    **(i) WHERE AGENTS OWN FILES IN PARALLEL, ANY STATEMENT ONE FILE MAKES ABOUT ANOTHER NEEDS A SETTLE POINT.** File ownership prevents write conflicts and does nothing about read staleness. Measured: a seat wrote comments in one file asserting what a companion file declares and emits. The assertions were true of the branch, true of the staged index, and false by the time the companion's own seat had finished. Five of six regressions in that file were that one mechanism, and no single seat could see it, because each owned only its own file. Pipelining for throughput is still right; add a reconciliation pass after all seats are done, which re-verifies every cross-file claim against the settled tree.

    **(j) A run killed by CAPACITY looks exactly like a run wedged by its own SHAPE, and the needle you search for decides which one you see.** Measured, and this is the clause the rest of the item nearly got wrong. A fan-out of 85 verifiers was recorded as a structural stall on the strength of two zeros: across its 94 transcripts there were zero occurrences of "API Error" and zero of "usage limit". Both zeros were true. Neither was informative, because the harness writes **"You've hit your session limit"**, which neither needle matches. Re-measured against the records the harness itself FLAGS as errors rather than against an invented phrase: **71 of the 94 agents carried exactly that line, 22 returned a result, and 1 did neither.** The run died of capacity. This fleet had already recorded the same cause once, 29 of 30 agents on a session limit, and did not recognise it the second time.

    Three things follow, and the first is the general one. **Enumerate the harness's own error records; do not grep for a phrase you expect.** A zero from a needle you invented is not evidence of absence, it is evidence that you guessed the wording. **State the search string in the finding**, so the next reader can see what the zero was a zero of. And **before concluding that a run wedged, count how many of its agents failed**, because a capacity failure and a design failure look identical on a progress display and call for opposite responses: one wants a smaller run, the other wants a different shape.

## What T3 deliberately does NOT require

No 11-element structural close, no mid-flight pause sub-procedure, no multi-module review cadence, no multi-phase plan with sub-cycles (all T4-only). Pre-drafted handover skeletons optional at T3, mandatory at T4.

## Worked example

A personal-blog rebuild project with a Cloudflare deploy step added; or any internal compliance-planning project at the moment it picks up its first irreversible-action enumeration. Handover gains the `Audit-pass owed for THIS session` footer; irreversible-action list lands in CLAUDE.md §6; first anomaly captured as OBS row inline. Standing-rule discipline applied throughout: anomaly-first triggered at first contradictory signal; regulator-presentable exactness enforced when GDPR cookie-banner content changed; best-practices-first informed implementation-path choice; lessons promoted from a 3-time-recurring handover note to a one-line standing rule.

## Hand-off to next tier

Project becomes mission-critical regulated, regulator can compel artefacts, failure is reportable to a national supervisor (capital-markets / data-protection / banking / insurance authority), or a wrong calculation triggers a regulatory finding → T4. Add `tier: T4` to project CLAUDE.md.

Project needs multi-phase plan with sub-cycles (S-cycle, E-cycle, sprint cadence) → T4 cadence applies.

T4 NEVER auto-detects (D-MET-8). Operator promotes by editing CLAUDE.md or typing `/vc-roe:tier T4`.
