# Methodology slice: T4, mission-critical regulated (cumulative T0 + T1 + T2 + T3 + T4)

First line of EVERY reply from the time this slice is loaded (whether at SessionStart or mid-session via `/tier`, `/raise-tier`, or `/lower-tier`) until session end MUST be exactly the following literal text (NO surrounding backticks, NO surrounding quotes, NO code block). v1.13.0 clarifies: the rule applies to every reply, not only the first reply after slice load.

Detected tier: T4 (S<x>/C<y>), <label>. Override with /vc-roe:tier <T0..T4> if wrong.

## What T4 is

A project where a regulator (HCMC, ESMA, EBA, EIOPA, national DPA, internal audit body) can compel production of artefacts. A wrong calculation, missing audit trail, or missed deadline triggers a regulatory finding or personal-conduct issue. A project that ships infrastructure carrying real money or real personal data.

T4 is reached only via explicit operator decision: `tier: T4` sentinel in project CLAUDE.md (persistent), or live `/vc-roe:tier T4` (one-session). Auto-detection caps at T3 per D-MET-8. Tier inflation alienates the operator more than tier deflation misses regulatory evidence (the latter is recoverable next session, the former erodes trust). Full canonical: the canonical methodology specification v4.1 §2 T4.

### Added at T4: the eleven-element structural close (abstract shape per D-MET-12)

The canonical T4 specification describes the SHAPE of a T4 close. It does NOT mandate specific artefact paths or technologies. Each T4 project chooses its own analogues.

1. **Regression floor verified** at session close. Project defines its regression floor (test suite, smoke test, latency check, compliance probe, backtest). Session close says: ran it, here is the result, here is the exit code or pass count.
2. **Change log entry** appended to a project-canonical change log (`BUILD_LOG.md`, `CHANGELOG.md`, project-specific).
3. **Operational runbook update** if operating procedures changed; if unchanged, state explicitly in negative scope.
4. **Compliance trace update** if compliance-relevant behaviour changed. Regulator-presentable exactness rule applies.
5. **Public-contract verification** if project exposes an API, file format, or other public contract. Lint clean.
6. **Architecture decisions captured** in change log (always) and architecture document (if architecture-grade). Free-form ADR format.
7. **Architecture-section row updated** if scope evolved within multi-phase plan (S-cycle, E-cycle, sub-cycle).
8. **Next-handover skeleton filled in**, with next-chat opening prompt rendered as fenced block in final chat message of closing session. Chat-render is a separate obligation from writing it into the handover; never substitute one for the other.
9. **User-facing or stakeholder-facing docs reviewed** for any drift from new behaviour.
10. **Final smoke check** passed before change log is closed. Project-defined live verification (brain-restart + `/health` probe; dev-server-renders-home-page; contract-validator-emits-clean; whatever fits).
11. **Change log written last**, after all other artefacts are stable.

### Plus three sub-procedures

- **Mid-flight pause sub-procedure.** Significant scope shift mid-session: stop, document the shift, re-confirm with operator before continuing. The pause is a confirmation gate, not a courtesy.
- **Multi-module review cadence** for project's own methodology document. Default: every five sub-cycles.
- **Pre-drafted handover skeletons** for next N sessions if project is on a known phase trajectory.

## Reference instance shape

The plugin does NOT ship a reference-instance file; that document lives in each operator's own working directory. The shape an operator-side reference instance typically takes:

| Abstract element | Typical instantiation |
|---|---|
| Regression floor | language-native test runner full pass + targeted regression of changed area |
| Change log entry | `BUILD_LOG.md` or `CHANGELOG.md` row appended after smoke check passes |
| Operational runbook | `RUNBOOK.md` if ops changed; otherwise stated in negative scope |
| Compliance trace | `COMPLIANCE.md` traceability-matrix update for any new auditable event type, one row per event |
| Public-contract | `openapi.yaml` (or equivalent contract spec) + lint clean |
| Architecture decisions | change-log row always; architecture-doc / ADR row if architecture-grade |
| Architecture-section | multi-phase-plan row in the spec for any sub-cycle that evolved scope, and for any enforcement-grade change |
| Next-handover skeleton | `handovers/session-(NN+1)-opening-prompt.md` |
| User-facing docs | reviewed for drift from new behaviour |
| Final smoke check | service restart + health probe + targeted route exercise |
| Change log written last | yes |

Each T4 project picks paths that fit its own stack. The methodology mandates the SHAPE of the close, not the specific filenames or technologies.

## What T4 deliberately does NOT require

T4 does NOT mandate any specific reference-instance artefacts; each T4 project keeps its own change-log path, runbook path, compliance-trace path, contract location, ADR format. T4 does NOT require slash-command override every session (once `tier: T4` is in CLAUDE.md, every session in that project starts at T4). T4 does NOT mandate any specific tooling, language, runtime, or platform.

## Worked example

A regulated-API project close instantiates elements 1 to 11 exactly as the reference table above shows. Element 3 had nothing to record, so the runbook was declared unchanged in negative scope. Element 8 was both written into the handover and rendered as a fenced block in the final chat message, two obligations rather than one. Element 11 was written last, after every other artefact was stable. Mid-flight anomalies were logged inline as they appeared, anomaly-first each time, with pause-and-probe rather than log-and-continue.

## Hand-off, there is no T5

T4 is the top of the matrix. If a project somehow grows beyond T4 (multi-organisational, multi-jurisdictional, with audit obligations across regimes), split into multiple T4 projects coordinated by a higher-level governance structure. The methodology does NOT prescribe what that governance looks like; out of scope.
