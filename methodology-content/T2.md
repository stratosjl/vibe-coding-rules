# Methodology slice: T2, small project (cumulative T0 + T1 + T2)

First line of EVERY reply from the time this slice is loaded (whether at SessionStart or mid-session via `/tier`, `/raise-tier`, or `/lower-tier`) until session end MUST be exactly the following literal text (NO surrounding backticks, NO surrounding quotes, NO code block). v1.13.0 clarifies: the rule applies to every reply, not only the first reply after slice load.

Detected tier: T2 (S<x>/C<y>), <label>. Override with /vc-roe:tier <T0..T4> if wrong.

## What T2 is

Multi-session. Persistent state. Real consequences. Has its own working directory under `OWN/` or `000-AI/`. cowork v2.1 Session Continuity Protocol applies in full. Full canonical: the canonical methodology specification v4.1 §2 T2.

## Cumulative requirements

**Inherited (T0 + T1):** humanized-text always-on (English + Greek); plan-first; verify-with-evidence; confirmation-gate for irreversible actions; capture-lessons inline; negative-scope at end.

### Added at T2 (cowork v2.1 Session Continuity Protocol)

1. **`<project>/docs/decisions.md`** — table with stable `D-N` IDs (never renumbered, never deleted). Row: ID, date, status (LOCKED/SUPERSEDED), one-paragraph decision text including reason. Reverse via new SUPERSEDED row + one-line resolution note; never silent edit.
2. **`<project>/docs/open-issues.md`** — table with stable `I-N` IDs. CLOSED rows stay as historical record (date + resolution note; never removed).
3. **Per-session close handover** at `handovers/session-NN-handover-YYYY-MM-DD.md`. Past tense. Sections: accomplishments, what changed on disk, verification, two-pass matrix, lessons, negative scope. Target 1–3 KB; ceiling 5 KB; collapse the file table into a one-paragraph "what changed" prose block when the session is small (CA3 at v0.1.7).
4. **Per-session opening prompt for the NEXT session** at `handovers/session-(NN+1)-opening-prompt.md`. Imperative tense. Sections: read-order, pre-next-chat verification block, today's agenda, standing rules in force. Designed to paste verbatim into a fresh chat.
5. **Pre-next-chat verification block** at bottom of every handover: 3 to 6 numbered checks (file present, version stamp, build status, last commit hash). The opening prompt references it. **Since v1.26.0 each check is written as a command to run and the output that passes it** ("Run `git log -1 --format=%h`; expect `<hash>`"), never as a bare assertion ("the build is green"). An assertion can only be believed; a command with its expected output can be judged from what is shown, by the next session, by a reviewer, and by a goal evaluator that reads only the conversation and runs nothing itself (item 17).
6. **[EXAMPLE-PROJ] five-step session close**: handover → opening prompt → decisions update → open-issues update → lessons capture. All five at session close, no exceptions.
7. **Brainstorming HARD-GATE convention** available per project. Lock when deliverable shape is open; release on explicit operator decision once shape converges.
8. **Session-health heartbeat (every 30 min wall-clock).** Surface a 5-line status: session goal restated; scope coverage; anomaly status (signals not yet captured as OBS rows); side-questions still open; long-running ops without recent status echo. Catches scope drift, accumulated unaddressed anomalies, forgotten side-questions, stale process state in long chats with many short ops. Distinct from the operation-scoped long-process status check. Standing rule: `feedback_session_health_heartbeat.md` (D-MET-33). Structural support at v0.1.7 via SessionStart anchor + UserPromptSubmit elapsed-time tag + Stop sentinel-grep (layered fail-safe per D-MET-39..D-MET-41). Since v1.20.0 the hook layer reports the clock rather than demanding the block (I-9): a cadence that has elapsed reads as DUE, which is a clock state and not a violation. The heartbeat itself remains the requirement; when you emit it, end it with the literal sentinel `[heartbeat-fired:T+<n>m]` so the clock advances.
9. **Session sweep paragraph at handover (T2+ floor).** One qualitative paragraph at the bottom of every handover answering three questions: did we ship what we set out to ship; did anything need to land in the project idea bank; did anything need to land in `open-issues.md`. T3+ supersedes with formal Pass 4 in four-pass matrix. Standing rule: `feedback_traceability_matrix.md` T2+ section (D-MET-34).
10. **Anomaly-callout inline (CA4 at v0.1.7).** When a signal does not match expectations within a turn (test failure unrelated to the change, schema mismatch, surprising tool output, broken pre-existing assumption), surface it inline within the same turn. No formal OBS table at T2; one-line callout suffices. The heartbeat catches missed ones at the cadence point. Bridges T3's anomaly-first reflex into the T2 floor without the formal table burden. Standing rule reference: `feedback_anomaly_first_reflex.md` (T2 lighter form; D-MET-43).
11. **TaskCreate for plans with three or more discrete steps (CA5 at v0.1.7).** Use the TaskCreate tool to track multi-step plans. Mark tasks `in_progress` when starting, `completed` when done. Aligns with the harness's existing TaskCreate reminder; preferred over ignoring it (D-MET-44).
12. **Subagent strategy for parallelism and context hygiene** (added v0.2.0; closes OBS-MET-L slice/canonical gap; cowork v2.1 rule). Use subagents when the work has genuinely independent parts, OR when a piece of work would balloon the parent context. Each subagent gets one focused objective, explicit file/scope ownership, a self-contained prompt, and a clear deliverable format. Trust but verify the subagent output before relaying it. Standing rule reference: `feedback_anomaly_first_reflex.md` (anomaly detection in subagent output) + the v2.1 baseline.
13. **Tier-persistence in handover + opening prompt + project CLAUDE.md** (F-MET-18 at v0.2.0; D-MET-38). Every T2+ session-close handover gains a `## Methodology tier` section near the top with four lines: tier in force at session close; source (auto-detected / sentinel / live override); changed mid-session (Yes/No with reason); project-level default per CLAUDE.md. Every T2+ next-session opening prompt's standing-rules section gains an `Expected tier at session open: T<N>` line plus a verification-block check. Every T2+ project's CLAUDE.md gains a `## Methodology tier` section with one paragraph stating the project-level tier and rationale (multi-machine / multi-month / regulatory exposure / etc.). Tier changes are documented in `decisions.md` (intentional) or `open-issues.md` (auto-detected drift for operator confirmation).
14. **Bounded project-brain snapshot (added v1.13.0; `feedback_bounded_project_brain.md`).** The auto-loaded project memory file (`CLAUDE.md`, or the tier's equivalent project brain) is a snapshot rewritten at each close, never an unbounded append log. The harness prefixes `CLAUDE.md` to every prompt and every subagent dispatch and warns then truncates past its size threshold (~40 KB at time of writing), so an append-and-grow status block silently degrades every turn once it crosses the line. Structure the file as: a current-state snapshot (identity, counts, load-bearing invariants, drift baselines, open items, pointers) plus the most recent sessions inline; older per-session narrative lives in an indexed sidecar (for example a `docs/status/` folder with an `INDEX.md`, or the per-session handovers), not pasted into the brain file. At each close, overwrite the snapshot (counts, state, as-of date), write the session's full record to the sidecar and index it, keep a size-governed window of the most recent sessions inline, and evict the oldest inline entry to its own file when the brain file nears the threshold. The window is governed by size, not a fixed count, so the file is self-bounding and can never cross the limit. This supersedes any "append one paragraph per session and roll the oldest off" maintenance pattern, which bounds the session count but not the byte size: each appended paragraph that re-states the cumulative invariants grows the file at the same rate it is rolled, so the file floats at the threshold indefinitely. Target a band comfortably under the threshold and use the headroom for useful recent state rather than padding. Full audit-trail obligations are unaffected: the per-session record (handover plus the sidecar entry) remains the change log; only the unbounded inline accretion is retired.

15. **A handover is re-audited if anything lands after it is written (added v1.21.0).** A handover is a claim about the state of the work at close. Any result that arrives after it is written, a late test run, a returning background job, a review that reports in, a colleague's reply, makes that claim stale in the one place a reader trusts most. **Before the session actually ends, re-read the handover itself against everything now known, not just the issue register.** Updating the register and leaving the handover is the common failure: the register is consulted by someone who already knows to look, whereas the handover is what the next session reads *first* and acts on without checking.

    The recorded failure mode is not a missing entry but a **contradicted instruction**: a handover told the next session to run a process, and a result arriving afterwards established that the process must not be run until several defects were fixed. The register had them; the handover still said "run it". A stale handover is more dangerous than an incomplete one, because it is confident.

    **The check is cheap and mechanical.** Enumerate the open items in the register, then confirm each one is either referenced in the handover or deliberately excluded, and that no instruction in the handover is contradicted by an item. If anything lands after that check, run it again. The last artefact written must be the last artefact audited.

16. **Every handover carries the next session's opening prompt, or a pointer to it that resolves (added v1.21.0).** The handover and the opening prompt are two halves of one handoff, and separating them is how a next session starts from the wrong place. Either the prompt is inline in the handover, or the handover names the exact path to it and **that path is verified to exist before close**. A pointer to a file that was never written is worse than no pointer, because the reader stops looking.

    This is not satisfied by rendering the prompt in the closing chat message alone. Chat scrollback is not an artefact: it is not in the repo, it does not survive a new machine, and it cannot be read by whoever picks the work up. Where a tier also requires the chat-render, the two are separate obligations and neither substitutes for the other.

17. **The opening prompt ends with a ready-to-paste goal (added v1.26.0; Claude Code only).** When the project's sessions run in Claude Code, the opening prompt for the next session ends with a `## Goal` section holding one fenced block that starts with `/goal `. Claude Code's `/goal` keeps a session working, turn after turn, until a small model reading the conversation judges the condition met, so the operator no longer has to push each step. On another harness, omit the section.

    The condition is capped at 4,000 characters and opening prompts are usually longer, so **the goal points at the prompt file instead of copying it**, and lists what "done" means: the pre-next-chat verification items run with their output shown (item 5), and the tier's session close. Shape:

    ```
    /goal Run session <NN> of <project> as written in handovers/session-<NN>-opening-prompt.md. Done only when all of this is shown in this conversation:
    1. Pre-next-chat verification items 1 to <k> run, each with its output shown.
    2. <the agenda items that must land this session>.
    3. Session close done: <the tier's close artefacts>.
    Ask me before any confirmation-gated action or scope change; stopping to ask me counts as done. Or stop after <N> turns.
    ```

    Four things in it are load-bearing. **"Shown in this conversation"**, because the evaluator runs no command and reads no file, so a result it cannot see is a result it cannot count. **The prompt's own filename**, so a goal copied from the previous session's prompt is caught. **The stop-to-ask clause**, because a goal is built not to stop, and a question to the operator must count as a legitimate end. **A bound**, because none is built in; a resumed goal restarts its turn count, so the bound applies per sitting.

    Before close, run the plugin's checker on the prompt and keep its output with the close evidence. It checks the section, the 4,000-character cap, the filename, the clause, the bound and the evidence wording, and exits non-zero on any miss:

    ```
    python3 "$(find "$HOME/.claude/plugins" -name check-goal-block.py -path '*vc-roe*' -type f 2>/dev/null | sort -V | tail -1)" handovers/session-<NN>-opening-prompt.md
    ```

    `/clear` removes an active goal, and `--continue` or `--resume` restores it. Behaviour across compaction is not documented, so after a compaction check the goal indicator before relying on it.

### Added at T2: a check's CANNOT-RUN must never render as its PASS or its FOUND-A-DEFECT (added v1.27.0)

T2 is the first tier that commits checks to the repository, so it is the first tier where a check can go missing without anyone noticing. **A check that cannot run must be distinguishable, from its output alone, from a check that ran.** Three rules, and the third is the one that is routinely skipped.

**1. A committed check may not read or import anything outside the repository and its declared dependencies.** Resolve every path relative to the file itself, `Path(__file__).resolve().parent`, never an absolute path into a temp, home, session or scratch directory. Where a check genuinely needs operator-local runtime state, mark the line with the reason, so that adding one is a decision rather than an assumption.

**2. A check must distinguish CANNOT-RUN from FOUND-A-DEFECT with different exit codes, and a regression floor must treat cannot-run as NOT-RUNNABLE rather than folding it into either pass or fail.** The convention this methodology uses:

| code | meaning |
|---|---|
| 0 | ran, nothing wrong |
| 1 | ran, found a defect |
| 2 | usage error: the CALLER is wrong |
| 3 | NOT-RUNNABLE: a dependency is missing, the ENVIRONMENT is wrong |

Do not renumber codes that already discriminate correctly; add 3 where a collision exists.

**3. The negative test for a check includes REMOVING ITS DEPENDENCY and asserting the cannot-run code, not only corrupting its input.** Corrupting the input exercises the arm that already works. This is the rule that gets left out, because a passing input-corruption test looks like a proven guard.

**Measured 2026-09-04**, on a T4 regulated project standing up a regression floor. A guard committed under `bin/` opened by inserting an absolute path into a session-scoped temp directory on `sys.path` and importing a module that existed nowhere else on the machine, written by a session that had ended three weeks earlier. It ran correctly only because the operating system had not yet swept that tree. `ModuleNotFoundError` exits 1; the guard used 1 for "this document has a structural defect". **So on the day the temp is swept, a regression floor reports a failing document and the investigation starts in the wrong place.** The guard's disappearance renders identically to the guard firing.

The repair is worth copying: the two functions the guard needed were **copied verbatim** into a tracked module rather than reimplemented, because a rewritten structural matcher had already cost that project once, a tag regex with no name boundary counting `w:tcPr` as `w:tc`. All nine tracked inputs produced byte-identical output and exit codes before and after the swap, and the negative control was to hide the module and watch the guard report cannot-run.

**The general form, which is not about temp directories:** any check whose dependency failure and whose finding share an exit code. A linter that cannot load its config. A test runner with a missing fixture. A schema validator whose schema is gone. A hook whose helper moved. In every one of them the loud symptom points at the subject rather than at the instrument.

## What T2 deliberately does NOT require

No audit-pass policy, no formal lessons-promotion path, no irreversible-action enumeration in CLAUDE.md, no regulator-presentable exactness rule, no formal anomaly-first reflex with OBS-row capture (all T3+; T2's anomaly-callout inline rule is the lighter floor per item 10). No 11-element close, no mid-flight pause, no multi-module review cadence, no pre-drafted handover skeletons (all T4-only).

## Hand-off to next tier

Project takes irreversible production action (deploys, force-pushes, schema migrations, external writes, content publication) → T3.

Project picks up a second regulatory keyword in CLAUDE.md → C2 → T3.

Project grows multi-machine, multi-stakeholder, or multi-month → S3 → T3 (or T4 with explicit override per D-MET-8).
